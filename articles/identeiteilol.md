## はじめに

普段自分がどれだけのデータを、自分の手の届かない場所に置いているか、考えたことはあるでしょうか。

Googleカレンダーの予定、Dropboxに突っ込んだファイル、SNSに書いた数年分の投稿。これらは全部、どこかの企業のサーバーの上にあります。自分のものだと思って使っていますが、実際に決定権を持っているのは自分ではありません。

利用規約が変わっても文句は言えるものの覆せません。サービスが終了したらデータごと消えます。アカウントが凍結されたら、蓄積してきたものが全部一瞬でアクセス不能になります。普段はそんなこと考えもしないと思います。自分もそうでした。

でもTwitterがXになった時、これを急に意識した人は多かったのではないでしょうか。ブランドが変わり、方針が変わり、自分の発言やフォロワーとの関係性が、一企業の一存でまるごと書き換えられてしまう。あの感覚です。普段は空気のように使っていたサービスが、実は自分のものではなかったと気づかされる瞬間でした。

こういう「クラウドに全部預けてしまう」設計は、実はWebが最初に目指していた形とは違います。そしてこの問題に、他でもないWebの生みの親が正面から取り組んでいるプロジェクトがあります。Solidといいます。

## Solidとは何か

[Solid](https://solidproject.org/) は、Webの発明者であるTim Berners-Leeが主導している、データの所有権をユーザーの手に取り戻すためのオープンな仕様群です。W3C(World Wide Web Consortium)出身のエコシステムで、[Inrupt](https://www.inrupt.com/) という会社が実装を進めています。

Berners-Lee自身、なぜこれを始めたのかをいろんな場所で語っています。彼のTEDトーク[「次のWebの大きな飛躍」](https://www.ted.com/talks/tim_berners_lee_the_next_web)を聞くと、彼が抱いていた危機感がよくわかります。Webはもともと「誰もが分散的に情報を発信し、コントロールできる空間」として設計されました。それが結果として、少数の巨大プラットフォームにデータが吸い上げられていく構造になってしまいました。これは技術的な必然ではなく、設計の選択が積み重なった結果だ、というのが彼の主張です。

正直に言うと、生みの親本人がここまで危機感を持って軌道修正しようとしているのは、なかなか珍しいことだと思います。

### 発想を逆転させる

普段使っているWebアプリの構造をシンプルに書くとこうなります。

```
[アプリ] ── データを所有 ── [ユーザー]
```

アプリ側(Google、Meta、OpenAIなど)がデータを持っていて、ユーザーはそこに間借りしているだけです。契約を切られたら終わりという意味では、賃貸に住んでいるのと似ています。

Solidはこの関係を逆にします。

```
[ユーザーのPod] ── データを所有
       ↑
   アクセス許可
       ↓
    [アプリA] [アプリB] [アプリC]
```

ユーザーは自分専用のデータストアを持ちます。これをPod(Personal Online Datastore)と呼びます。アプリはこのPodに対して、ユーザーが許可した範囲だけアクセスできます。カレンダーアプリを乗り換えても、SNSを乗り換えても、データ自体は自分のPodに残り続けます。賃貸ではなく持ち家に近い感覚と言えばわかりやすいかもしれません。アプリの方が出入りする側になります。

## 技術的な仕組み

ここが個人的には結構好きなポイントなのですが、Solidの仕様はゼロから新しい技術を作っているわけではありません。既存のWeb標準の上に組み立てられています。

主な要素はこの3つです。

**[WebID](https://www.w3.org/2005/Incubator/webid/spec/identity/)**
URLベースの分散型アイデンティティのことです。特定のプラットフォームに登録するのではなく、自分のURLそのものが自分の身元証明になります。GoogleアカウントやXアカウントに紐づいた「身分」ではなく、自分でホストしているURLが自分のIDになるイメージです。

**[Linked Data Platform (LDP)](https://www.w3.org/TR/ldp/)**
RDFという形式でデータを構造化して、意味的に繋がった形で保存する仕組みです。データがバラバラのサイロに閉じ込められるのではなく、お互いに参照し合える形で残ります。

**[WAC (Web Access Control)](https://solid.github.io/web-access-control-spec/) / [ACP (Access Control Policy)](https://solid.github.io/authorization-panel/acp-specification/)**
誰が、どのデータに、どういう権限でアクセスできるかを細かく決める仕組みです。友達には見せるけど職場には見せない、といった粒度の制御をユーザー自身の手で行えます。

まとめると、Solidは「新しいSNSを作りました」という話ではなく、Webのデータレイヤー自体を作り直そうとしているプロジェクトだと理解した方がしっくりきます。

自分で試してみたい方向けに言うと、[Community Solid Server](https://github.com/CommunitySolidServer/CommunitySolidServer) というオープンソース実装が公開されています。自分のマシンやVPSに立てれば、その日のうちに自分のPodを持てます。

## なぜ今これを書こうと思ったか

正直に言うと、この記事のきっかけはSolid単体の話ではありませんでした。最近、手元のV100でQwenのオープンウェイトモデルを動かそうとあれこれ試していて、その過程でふと気づいたことがあります。

ChatGPTやClaudeのようなクラウドAPIに全面的に頼ると、モデルの仕様変更、利用規約の変更、最悪の場合はサービスそのものの停止という形で、自分の「考える力の外部委託先」を丸ごと一企業に握られることになります。これに対して、[Llama](https://www.llama.com/)や[Qwen](https://huggingface.co/Qwen)、[Mistral](https://mistral.ai/)のようなオープンウェイトモデルを自分のマシンで動かす人が増えてきています。

これはSolidの話と、構造がほとんど同じだと思いました。データの主権と、知能の主権。呼び方は違いますが、根っこにある問題意識は一つです。自分に関わる情報や能力を、外部の営利企業のインフラに預けきってしまうことのリスクにどう向き合うか、という話です。

## 弱点も正直に書いておきます

いいことばかり書いていても説得力がないので、課題も挙げておきます。

まず、エコシステムがまだ薄いです。Podに対応したアプリの数は、GoogleやMetaのエコシステムと比べたら話にならないくらい少ないです。

運用コストの問題もあります。自分のPodを立てて維持するには、それなりの技術知識とサーバー管理の手間がかかります。「結局クラウドの方が楽じゃないか」という現実は、正直まだ変わっていません。

あとはネットワーク効果の壁もあります。SNSやコラボツールは「みんなが使っているから自分も使う」という力学がかなり強いです。個人が分散型を選んでも、繋がる相手がいなければ意味が薄れてしまいます。

これは技術の限界というより、新しい仕組みが広がる時にいつも起きる話だと思います。Linuxも初期のオープンソース運動も、最初は「時間はあるけど多少の不便は気にしない」という少数の人たちから広がっていきました。Solidも今、たぶんその段階にいます。

## おわりに

Solidが提示しているのは、派手な代替プラットフォームではなく、決定権を自分の手元に置くという、地味だけど本質的な選択肢だと思います。

これは誰にでも勧められる話ではありません。多くの人は日々の生活を回すだけで手一杯で、データの主権なんて考える余裕はないでしょうし、それは全然おかしいことではありません。それでも、もし今少しでも時間的な余裕があるなら、こういう「依存しない選択肢」を一度自分の手元に持っておくことには意味があると思います。

何か大きな事件が起きてから慌てて動くより、先に避難先を作っておいた方がずっと楽です。TwitterがXになった時のことを思い出してみてください。あの時、既に自分のデータをどこかに逃がしていた人と、していなかった人とでは、たぶん見えていた景色が違ったはずです。
