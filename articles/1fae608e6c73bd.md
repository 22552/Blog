現在、インターネットを使うことはほとんど「Webを使うこと」と同義になっています。

検索、SNS、動画、ニュース、チャット、文書共有、開発ツール。多くのサービスがHTTP上に構築され、Webブラウザから利用できます。

これは非常に便利です。一方で、Webにあらゆる機能を集約した結果、単に文章を読むだけでも大量のJavaScriptを実行し、Cookieへの同意を求められ、広告やアクセス解析のために複数の外部サーバーへ接続する、といったことも珍しくなくなりました。

そこでこの記事では、Webを置き換えるのではなく、**HTTP以外のインターネットをもう一度選択肢として考える**という意味で「Post HTTP」という言葉を使います。

題材にするのは、1991年に登場した **Gopher** です。

## そもそもGopherとは

Gopherは、インターネット上で文書やファイルを公開・取得するためのプロトコルです。

WebのHTTPと同時期に登場しましたが、現在主流になっているのはHTTPです。そのため、一般的なブラウザだけを使っているとGopherに触れる機会はほとんどありません。

Gopherサーバーへアクセスすると、基本的には次のような情報が返ってきます。

* テキスト文書
* ディレクトリ
* 別のGopherサーバーへのリンク
* ファイル
* 検索サービス

Webページのように、サーバー側がページ全体の見た目を自由にデザインする仕組みではありません。

サーバーは「これは文章」「これはディレクトリ」「これはリンク」といった情報を返し、それをどう表示するかは主にクライアント側が決めます。

つまり、

**コンテンツと表示方法が比較的はっきり分離されています。**

これは現代のWebとの大きな違いです。

## Gopherの通信はかなり単純

Gopherの仕組みはHTTPと比べても非常に小さいものです。

大まかには、

1. TCPでサーバーへ接続する
2. 欲しい項目を示す文字列を送る
3. サーバーから結果を受け取る

という流れです。

たとえばGopherのメニューには、おおむね次のような情報が並びます。

```text
1About	/about	example.org	70
0README	/readme.txt	example.org	70
1Projects	/projects	example.org	70
```

先頭の文字は項目の種類を表します。

`0` ならテキストファイル、`1` ならディレクトリ、といった具合です。

その後ろに表示名、取得するときに送るselector、接続先ホスト、ポート番号が続きます。

HTMLのDOMを構築してCSSを適用し、JavaScriptを実行する、といった仕組みとはかなり違います。

Gopherで文章を配信したいだけなら、必要な仕組みもそれだけ小さくできます。

## なぜ今Gopherを見るのか

「昔のプロトコルが珍しいから」というだけではありません。

面白いのは、Gopherの技術的な制限によって、現在のWebとはかなり異なる利用環境が形成されていることです。

### JavaScriptを前提にしない

Gopherには、WebブラウザのJavaScriptに相当する標準的な実行環境がありません。

そのため、ページを開いた瞬間にサイト側のコードが大量に実行される、というWebで一般的な構造そのものがありません。

もちろん、その代わりWebアプリのような高度なUIは作れません。

つまりこれは単純な長所ではなく、

**できることを意図的に狭くしたプロトコル**

として見るのが適切です。

### サーバー側が表示をほぼ支配しない

WebではCSSやJavaScriptを使って、サイト側がUIを細かく指定できます。

Gopherでは、同じサーバーでもクライアントによってかなり異なる見た目で表示できます。

ターミナルで見ることもできますし、GUIクライアントで見ることもできます。

Webが「サイトを見る」仕組みに近いのに対し、Gopherはどちらかというと**サーバーから情報構造を取得する**仕組みに近いと言えます。

### トラッキングに使える機能が少ない

現代のWebでは、Cookie、JavaScript、ブラウザAPI、埋め込みリソースなど、ユーザーの状態や行動を扱える機能が大量にあります。

これらはログインやショッピングカートなど便利な機能にも必要ですが、広告計測やユーザー追跡にも利用できます。

Gopherにはそのような高度なブラウザ環境がありません。

ただし、

**「Gopherなら匿名であり、追跡されない」という意味ではありません。**

通常のGopher接続では、サーバーから接続元IPアドレスは見えますし、サーバー側でアクセスログを保存することもできます。そしてGopher自体は標準では暗号化されません。

重要なのは「プライバシーが自動的に保証される」ことではなく、Webと比較してクライアント側で収集できる情報や実行できる処理がかなり少ないことです。

## 広告がないのはプロトコルのおかげではない

現在のGopher空間を探索すると、商業Webでよく見るような広告ネットワークにはほとんど遭遇しません。

しかし、ここは区別する必要があります。

**Gopherだから広告を掲載できないわけではありません。**

メニューに広告へのリンクを入れることはできますし、広告文そのものを表示することもできます。

それでも現在のGopherで広告がほとんど見られないのは、技術的な制限だけではなく、利用者や運営者の文化による部分が大きいでしょう。

現在もGopherサーバーを動かしている人の多くは、大規模な収益化サービスを構築するためではなく、

* 個人の文章を公開する
* 技術的な実験をする
* 古いインターネット文化を維持する
* 自分の小さな情報空間を持つ

といった目的で運営しています。

検索エンジンやクライアント、公開サーバーなども、個人や小さなコミュニティによって維持されているものがあります。

これはプロトコルの仕様ではありません。

**現在のGopherコミュニティが形成している文化です。**

そこは分けて考えたほうがGopherの面白さを正確に理解できます。

## Webはなぜここまで複雑になったのか

一方、Webが複雑になったのにも理由があります。

HTTPとWebブラウザの上で、

* 動画編集
* 3Dゲーム
* オフィスソフト
* ビデオ会議
* SNS
* オンライン決済

まで動かそうとしているからです。

現在のブラウザは、もはや単なる文書ビューアではありません。

巨大なアプリケーション実行環境です。

広告やトラッキングだけを原因としてWebが重くなったわけではありません。

しかし、Webが万能な実行環境になったことで、広告会社や分析サービスも非常に高度な仕組みを構築できるようになりました。

「文章を読む仕組み」と「アプリケーションを実行する仕組み」が同じブラウザに統合された結果、

**数KBの文章を読む場合にも、極端に高度なWeb環境を利用する**

という少し奇妙な状態になっています。

## GopherはWebの代替にはならない

ここまで読むと「では全部Gopherにすればいい」と思うかもしれませんが、それは現実的ではありません。

GopherはWebアプリケーションの代替ではありません。

たとえば、

* 動画配信サービス
* オンラインゲーム
* 高度な共同編集
* ECサイト
* Web IDE

などをGopherで再現することにはほとんど意味がありません。

Gopherが得意なのは、もっと小さな用途です。

文章を公開する。

ファイルを整理する。

日記を書く。

リンク集を作る。

小さな情報サービスを公開する。

このような用途では、「Webほど高機能ではない」ことが必ずしも欠点になりません。

## HTTP以外にもインターネットはある

Gopher以外にも、用途に応じたプロトコルはたくさん存在します。

たとえば、

* SSH
* IRC
* SMTP
* NNTP
* Gemini
* Finger

などです。

現在でも日常的に使われているものもあれば、かなり小さなコミュニティで維持されているものもあります。

インターネットは本来、

```text
Internet
├── HTTP
├── Gopher
├── SMTP
├── SSH
├── IRC
├── Gemini
└── ...
```

のように、IPネットワーク上で多数のプロトコルが共存する仕組みです。

HTTPはその一つです。

ただ、Webがあまりにも成功したため、ユーザーから見ると

```text
Internet ≒ Web
```

になりました。

ここをもう一度分離して考えてみるのが、この記事でいう **Post HTTP** です。

## Post HTTPとは

Post HTTPは新しい通信規格の名前ではありません。

HTTPを廃止しようという運動でもありません。

この記事では、

> すべてのインターネットサービスをWebに載せる必要があるのかを考え、用途によってHTTP以外のプロトコルも選択する

という考え方をPost HTTPと呼んでいます。

Webが最適ならWebを使えばいい。

単純なテキスト公開ならGopherでもいい。

小さな文書空間ならGeminiでもいい。

対話ならIRCという選択肢もある。

用途ごとに違うプロトコルが存在すること自体は、むしろインターネット本来の姿に近いものです。

## 実際にGopherを見てみる

ここまで仕組みを説明してきましたが、せっかくなので**実際のGopherへ接続してみましょう。**

現在も動いている代表的なGopherサーバーの一つに、Floodgap Systemsがあります。Gopherコミュニティを長年支えているサーバーで、Gopherの入門資料や検索エンジン「Veronica-2」、他のGopherサーバーへのリンクなどが公開されています。

### 方法1：Lynxから入る

Lynxはテキストブラウザですが、HTTPだけでなくGopherにも直接対応しています。

Lynxが入っている環境なら、

```bash
lynx gopher://gopher.floodgap.com/
```

を実行します。

するとWebページではなく、FloodgapのGopherメニューが表示されます。

そこには、

* Gopher初心者向け資料
* Gopherspaceの検索
* 公開Gopherサーバーの一覧
* ニュースや天気
* ファイルアーカイブ
* ゲーム
* 個人ページ

などへの項目があります。

Floodgapでは、Gopherspaceを検索するための **Veronica-2** も現在公開されています。Webにおける検索エンジンに近い役割を持つサービスです。

SDFのドキュメントでも、Gopherを見る方法として

```bash
lynx gopher://sdf.org/
```

が案内されています。

つまり、LynxではHTTPのWebサイトを見るのと同じブラウザから、そのまま別のプロトコルへ移動できます。

### 方法2：Bombadilloを使う

もう少し「Small Internet専用ブラウザ」らしいものを使いたければ、Bombadilloもあります。

```bash
bombadillo gopher://gopher.floodgap.com/
```

BombadilloはGopherだけでなく、GeminiやFingerにも対応したターミナルブラウザです。Debianでもパッケージとして提供されています。

ここが少し面白いところです。

```text
HTTP    → Web
Gopher  → Gopherspace
Gemini  → Geminispace
Finger  → Finger
```

という複数の世界を、一つのクライアントから行き来できます。

「インターネットブラウザ＝HTTPブラウザ」という感覚が少し崩れてきます。

### 方法3：普通のブラウザから見る

ChromeやSafariなどは現在Gopherを直接扱えません。

専用クライアントをインストールしたくない場合は、GopherとHTTPの間を変換する**Webプロキシ**を利用できます。

Floodgap自身がPublic Gopher Proxyを提供しているほか、SmolNet PortalのようにGopherやGeminiなどをWebブラウザから閲覧できるゲートウェイもあります。

たとえば `mozz.us` では、

```text
gopher://mozz.us
```

というGopherサーバーが現在も動いています。

運営者のMichael Lazar氏はGopherだけでなくGemini、Spartan、Finger、Telnet、Nexなど複数のSmall Internet系サービスを実際に公開しており、SmolNet PortalからWeb経由でもアクセスできるようにしています。

ただし、Webプロキシを使っている時点で通信自体はHTTP/HTTPSを経由しています。

Gopherそのものを体験するなら、LynxやBombadilloなどのネイティブクライアントを使うほうが分かりやすいでしょう。

### さらに、生のGopherを見てみる

Gopherの単純さを見るには、専用クライアントすら必要ありません。

Gopherは基本的にTCP上で動いていて、標準ポートは70です。

LinuxやmacOSなどで `nc` が使えるなら、Floodgapへ直接接続できます。

```bash
printf '\r\n' | nc gopher.floodgap.com 70
```

ルートメニューを要求するselectorは空文字列なので、ここではCRLFだけを送っています。

返ってくるのは、だいたい次のような構造のテキストです。

```text
1項目名	selector	gopher.floodgap.com	70
0文書名	selector	gopher.floodgap.com	70
i説明文	fake	gopher.floodgap.com	70
```

ブラウザが描画したHTMLではありません。

JSONでもありません。

Gopherのメニューそのものです。

たとえば、

```text
1Floodgap Home	/home	gopher.floodgap.com	70
```

なら、

```text
1
```

は「この項目はメニュー」、

```text
Floodgap Home
```

はユーザーに表示する名前、

```text
/home
```

は次にサーバーへ送信するselector、

```text
gopher.floodgap.com
70
```

は接続先です。

`/home` を取得したければ、

```bash
printf '/home\r\n' | nc gopher.floodgap.com 70
```

とするだけです。

HTTPのようなリクエストヘッダーを大量に組み立てる必要もありません。

概念的には、

```text
TCP接続
   ↓
selector + CRLF
   ↓
データが返る
   ↓
接続終了
```

です。

これだけでGopherを「閲覧」できます。

### GopherからGopherへ移動してみる

Floodgapのトップページには、他のGopherサーバーの一覧やVeronica-2があります。

そこから知らないサーバーを一つ選び、さらにその中のリンクを辿ってみます。

すると、

```text
Floodgap
   ↓
検索・サーバー一覧
   ↓
知らない個人サーバー
   ↓
その人の文章
   ↓
その人が紹介している別のサーバー
```

という形でGopherspaceを移動できます。

これは検索結果と推薦アルゴリズムを中心に移動する現在のWebとは少し違います。

リンク集や個人のメニューを辿って、別の個人サーバーへ移動していく使い方がかなり目立ちます。

実際に触ってみると、Gopherが単に「古いWeb」なのではなく、

**サーバーから構造化された情報を取得し、クライアント側で閲覧する、かなり異なる設計の情報空間**

だということが分かりやすくなります。

そして現在でも、その仕組みを面白いと思った開発者たちによってサーバー、検索エンジン、クライアント、ゲートウェイが維持されています。


## まとめ

GopherはWebより高機能なプロトコルではありません。

むしろ逆です。

できることは圧倒的に少ない。

しかし、

* 仕組みが単純
* クライアント側プログラムを前提としない
* 表示とコンテンツが分離されている
* トラッキングに利用できる機能が少ない
* 個人運営中心の小さなコミュニティが現在も存在する

という特徴があります。

現在のWebは便利ですが、広告、計測、巨大なJavaScript、プラットフォームへの依存といったものも日常の一部になりました。

それが嫌ならインターネットそのものをやめる必要はありません。

**Webの外へ出ればいい。**

インターネットにはHTTP以外のプロトコルもあり、その一部は現在でも実際に使われています。

Gopherを触ったからといってWebを捨てる必要もありません。

ただ一度、

「インターネットとはブラウザでWebサイトを見るもの」

という前提を外してみる。

そこから見える小さなインターネットは、現在のWebを考え直す材料としてかなり面白いはずです。
